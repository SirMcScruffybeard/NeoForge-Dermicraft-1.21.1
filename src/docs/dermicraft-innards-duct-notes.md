# Dermicraft Innards Duct Notes

Running log of decided design choices for the Innards Duct pipe system and the reasoning behind them. Add a new entry as decisions get made.

---

## Overview

**Status:** Core shape, capacity rules, and jam-clearing interaction confirmed. No implementation yet.

**What it is:** A lightweight automation transport system that moves **either items or fluids, never both at once on the same segment** — the mod's answer to hoppers/pipes for longer-distance or branching transport. Two block types: the **Innards Duct** (a dumb, single-purpose conduit segment) and the **Node** (the only place routing decisions happen). Deliberately kept cheap: no simulated travel of items/fluids through the pipe, no per-tick graph walks, no round-robin fairness logic baked into every segment.

**A Node is mandatory for any flow (confirmed) — no auto-detection anywhere.** A duct run has no way to infer which end is source and which is sink on its own; direction is only ever set explicitly, via a Node's In/Out button (see Node section, below). Practical consequence: a duct run with **no Node anywhere on it is inert by construction** — not a special case to detect or reject, just the natural default state of an unrouted run. This also means the Innards Duct itself needs zero decision-making logic of any kind, not just "no branching logic" — every transfer it ever carries was already fully decided by a Node.

**Upgrades are planned for both block types (confirmed direction, not yet designed).** Both Innards Duct and Node will get upgraded tiers later. **Implementation guidance:** build the block and block entity classes with inheritance in mind from the start — an abstract base per block type (e.g. `InnardsDuctBlockEntity`/`NodeBlockEntity`) that a future upgraded tier extends and overrides just the parts that change (buffer size, transfer rate, run length cap, etc.), the same shape the mod already uses for `MachineBaseBlockEntity` and the `TumorBlock` family, rather than duplicating logic per tier.

## Innards Duct (the segment)

**What it is:** A straight run connecting exactly two endpoints — either a Node or a block exposing an item/fluid capability. No buffer, no branching, no routing logic of its own. All the "smarts" live in the Node (see below); a duct run is just a conduit.

**Connection model:** 6-directional (N/S/E/W/U/D) connection state, same pattern as vanilla glass panes/iron bars — a duct connects automatically to a neighboring duct or Node, and to a neighboring capability-exposing block only if that face is open.

**Transfer mechanic:** No item/fluid travels step-by-step through intermediate segments. A run is resolved once (on placement/neighbor-change) to its two endpoints, and transfer is a direct push between those two capability handlers, ticked on a cadence rather than every tick (matching the 10-tick cycle already used elsewhere for machine processing).

**Mode lock — superseded (2026-07-10) by independent per-leg Item/Fluid toggles.** The original plan below (each run locking to ITEM or FLUID with a 10-tick idle threshold before it could switch) is **not what got built** — kept here for history only, see the Routing config section for the actual implemented mechanism.
~~Each individual duct run — not the whole Node-connected web — locks to **ITEM** or **FLUID** on first successful transfer, and won't accept the opposite type until it drains empty and goes idle. **Idle threshold: 10 ticks** before a run is considered free to switch modes. This is deliberately per-run rather than global: a single Node can have some legs carrying items and others carrying fluid simultaneously, since each run is independent.~~

**What actually shipped instead: independent per-leg Item/Fluid enable toggles, no lock at all.** Each connected leg has two additional booleans — Items on/off, Fluids on/off — fully independent of the leg's In/Out/Off direction and of each other; a leg can carry both, either, or neither simultaneously. **Both default OFF** (a leg set to In/Out carries nothing until the player explicitly enables a type — deliberately conservative, so nothing flows before the player has a chance to stop it). Rationale for dropping the lock entirely: it added real complexity (idle-timer tracking per run, a greyed "locked" button state) to solve a problem — items and fluid fighting over the same leg — that a simple on/off toggle per type solves more directly, without any risk of one type starving the other. Server load isn't a real concern: both types are already rate-capped per leg per `CRAFT_TICKS` cycle (`ITEM_TRANSFER_PER_CYCLE`/`FLUID_TRANSFER_PER_CYCLE`), so running both simultaneously on a leg just doubles a handful of already-bounded, non-per-tick capability calls.

**Size cap (confirmed): 64 blocks per run.** Enforced as a **placement-time rejection** — placing a duct segment that would extend a run past 64 members is refused outright, rather than allowed and truncated/erroring at runtime. Reasoning:
- The flood-fill/count itself is cheap regardless of size, so the cap isn't there to protect that.
- It keeps a duct run feeling like a local conduit rather than a base-spanning logistics backbone — thematically appropriate (guts don't pipeline across an entire factory) and avoids ever needing pumps/boosters, which would undercut the lightweight goal.
- 64 lines up with a familiar, easy-to-eyeball scale (roughly 4×4 chunks' worth of blocks).
- Nodes naturally break a build into many small independent runs instead of one sprawling network, so the cap rarely becomes a real constraint in practice — it's a guardrail, not an expected limitation.

**Visual model (confirmed):** Not a simple cube — needs a multipart blockstate (a central "post" model + one "arm" model per connected direction), the same shape vanilla uses for fences/glass panes/iron bars. NeoForge's `BlockStateProvider` has a built-in helper for this exact shape, so the multipart JSON and sub-models are generated rather than hand-written.

**Diameter (confirmed): thick, ~12-14px of 16** on unconnected ends — deliberately chunkier than the thin-pipe convention other tech mods use, to read as organic/intestinal rather than metallic. Stops short of full 16px so a duct run still reads as a distinct tube object with a visible seam/shadow gap against open air, rather than looking like a solid corridor wall.

**Corners (confirmed, as-built — no dedicated elbow):** corners render as **two arms meeting in the central node-hub**, the "free" fence/pane-style bend. The earlier plan for a dedicated 90° elbow model was **built, tested, and then dropped** — once the core became a smooth node-hub (see below), two arms plugging into that hub read fine as a bend, so the elbow was dead weight. The elbow model, blockstate, item model, registration, lang entry, and its icon texture were all removed. No elbow is needed at any tier.

**As-built rendering model (confirmed in-game):**
- **Node-hub core** — the core is a smooth **12px cube** (`[2,2,2]→[14,14,14]`), no directional ridges. A single un-rotated core can't present ridges that line up with arms from all six axes (a N/S-ridged core mismatches E/W and U/D arms — seen in-game), so the hub is deliberately smooth and the arms carry the ridges. Ridges "pause" at the hub, reading as vessels bundling into a node (fits the vessel lore).
- **Arms butt the hub, they do NOT penetrate it.** Arm boxes are `z0–2` (butting the hub face at z2), not `z0–5`. An earlier `z0–5` version buried 3px of arm inside the 12px hub; those buried faces sat ~1px behind the hub faces and **z-fought/bled through at grazing angles** (a real in-game bug that took several tries to pin down — the fix was shortening the arms to a butt joint, not nudging the hub or the ridges). The end piece's profile is likewise shortened to `z1–2` (flange stays `z0–1`).
- **Ridges pushed in 0.25** (outer faces at `2.25`/`13.75` instead of `2`/`14`). Originally added as a z-fight fix; kept because the user likes the slightly-recessed look. Not strictly needed now that the arms butt (the butt joint alone prevents the z-fight), but retained deliberately.
- **Multipart blockstate**: core always shown + an arm or end model per connected face, rotated (`y` for horizontal, `x` for up/down, same convention as `OuterfaceBlock`). Per-face connection state is a 3-value enum `DuctConnection` (NONE/PIPE/END): PIPE→arm toward a duct/Node, END→flange toward a capability block (machine/inventory).

**Textures (confirmed, simplified from the earlier two-texture plan):** **1 texture only** (`textures/block/innards_duct/innards_duct.png`, 64×64), single render layer, no separate tintable overlay, shared by all three models (core/arm/end). The texture is painted with its own natural color (light orange/light brown, "thin skin" look) — that's the permanent appearance for an **empty or item-mode run**, shown with no tint applied (identity/white multiplier). **Tint only activates for a run actively in FLUID mode**, recoloring toward the flowing fluid's `getTintColor()` — same mechanism as the bucket fill overlay (`registerBucketTint`), just applied to the one existing texture instead of a dedicated overlay layer. The natural shading/highlight variation already painted into the texture is what sells the "seeing fluid through thin skin" effect once multiplied by the fluid's tint color.

**Texture layout / UV convention (confirmed, as-built):** the shared texture is skin across the whole canvas **except a dark tube-opening design painted into the bottom-right 16×16 corner** (UV `[12,12,16,16]`). Faces are UV-mapped by role:
- **Skin faces** (all the outer/side faces, and the entire core) keep ordinary skin UVs — the core is all skin (never a visible open end in a built run, so no holes; confirmed correct in-game).
- **Tube-mouth bore faces** (the main tube cross-section at a genuine open end — arm tip, end flange) map to the full opening corner `[12,12,16,16]` so the big hole shows.
- **Ridge end-cap faces** (the tips of the four wall ridges at each mouth) map to the **solid-dark centre of the opening**, UV `[13,13,15,15]`, so the wall ends read dark and don't frame the hole in a pale border. Without this the openings looked too small (in-game finding). Applies to the 4 ridge ends each on the arm and the end.

**Lore / appearance rationale (confirmed):** the ridges running the length of the duct are **vessel/vein cords** under the outer skin membrane; a duct's dark open end is those **vessels seen in cross-section** — blood-dark, fluid-filled bundles cut flush. This is why the ridge end-caps are darker than the skin, and it reinforces the mod's fluid-transport premise (blends/slurries move *through* the vessels). Fallback framings if a future variant/tier wants a different read: **sphincter ring** (darker terminus = dense muscle gasket that grips the connection) or **lumen lining** (inner tissue darker than outer skin, like gut lining). Vessel-bundle is the default.

## Node (the smart bit)

**What it is:** The only block in the system that makes routing decisions, and the **only source of direction for any duct run** — see the mandatory-Node rule in Overview, above. Ducts run into and out of a Node; the Node decides which connected output run receives what, and holds a small relay buffer to decouple upstream/downstream timing.

**Single 1-block structure (confirmed).** Not a multiblock — one block, one block entity, same footprint category as any other machine.

**Non-directional placement (confirmed) — always faces the same way in-world.** Unlike Masticator/Effluentcer, the Node has **no `FACING`/`HorizontalDirectionalBlock` property** — same treatment as Skin Tank. This is deliberate: the block is isotropic on its four horizontal faces (see Textures, below), so there's no visual "front" for a placement-facing to anchor to, and a fixed single orientation means an arrow baked into the top texture always points true north, in every world, regardless of which way the player was facing when they placed it. This is what makes the compass-direction GUI (below) concretely readable against the real world instead of a purely abstract label.

**Textures (confirmed):** 5 side faces reuse the shared `skin_tank_end` texture (same reuse convention as Masticator/Effluentcer); the top face gets one new unique texture, with a north-pointing arrow baked in per the non-directional placement above.

**Buffer (confirmed): 1 item slot + 1000 mB fluid tank.** Used as a two-phase relay, not storage:
1. **Pull phase:** accept from a connected input run into the buffer, if empty.
2. **Push phase:** try to push the buffer's contents down the currently-enabled output(s) in the same tick, per the distribution mode below; if nothing currently accepts, hold and retry next tick.

The guardrail here is deliberate: the junction should always try to drain what it just pulled in on the same tick a valid output exists, so it never becomes a de facto storage box players start relying on instead of an actual tank.

**Direction labeling (confirmed): compass (N/S/E/W/U/D), not local (front/back/left/right).** Chosen specifically because the Node has no visual front to anchor local terms to (see non-directional placement, above) — compass directions are absolute, match the F3/map frame of reference players already have, and are honest about the block's actual left-right symmetry. (Masticator/Effluentcer's existing local-terms automation-face mapping is fine as-is — those blocks *do* have a visible front, so local terms work for them specifically.)

**Routing config (GUI) — no priority list (confirmed, replaces earlier priority-list idea):**
- One button per **connected** compass direction only — a face with no duct attached shows no button.
- Each connected button **cycles In → Out → Off** on click — the direction/leg-mode configuration surface, no separate enable checkbox or reorder controls at this layer.
- **Per-leg Item/Fluid toggles (as-built, implemented 2026-07-10, supersedes the mode-lock plan above):** two additional buttons, acting on whichever leg is currently selected (same selection model as the shared In/Out button) — one cycles that leg's item flow on/off, the other its fluid flow on/off. Both default off. Fully independent of the In/Out/Off direction and of each other. GUI layout: the Item toggle sits one grid step past the In/Out column, aligned with North's row; the Fluid toggle in the same column, aligned with South's row (mirroring the existing In/Out-above-Round-Robin column pattern). Textures: `item_button.png` / `fluid_button.png` for the ON state, the existing `no_use_button.png` reused for OFF, `null_button.png` when no leg is selected (or the selected leg isn't connected) — same fallback convention as the In/Out button. Networking: one new payload, `NodeTransferToggleClickPayload(pos, direction, fluid: boolean)`.
- **Global distribution mode, one toggle per Node: Round-Robin or Equal Spread** across whichever legs are currently marked Out. No priority ordering at all — if a player wants one leg favored over another, that's solved with plumbing (duct layout), not software. This is a deliberate scope cut from the earlier reorderable-priority-list idea, since tri-state per-direction buttons already cover everything a priority list was for.
- **Equal Spread partial-delivery rule (confirmed):** if an enabled output can't accept its full even share on a given push-phase tick, it gets whatever it can currently take and the undelivered remainder stays in the buffer for the next tick — no same-tick reallocation of the shortfall to other outputs. This is exactly the kind of case the buffer exists to absorb gracefully.
- **Two-Node conflicting-direction rule (confirmed):** if a duct run has a Node on both ends and their settings for that shared leg disagree (e.g. both Out, or both In), the run is treated exactly like "no valid destination this tick" — inert until a player fixes one side. No special conflict-resolution logic, consistent with the buffer's existing hold-and-retry philosophy.
- GUI icons needed: a direction glyph per connected button, plus whatever distinguishes the In/Out/Off cycle state and the Round-Robin/Equal-Spread toggle — kept as **separate small PNGs**, matching the existing `screen_parts/` convention (one file per widget piece, e.g. `arrow_background.png`/`arrow_fulll.png`), not a sprite sheet. Background/slot/tank chrome reuses existing `screen_parts` assets (`screen_background.png`, `item_slot.png`, `tank_and_slot.png`).

**Manual jam-clearing / testing (confirmed):** Players can interact with a Node's buffer manually, the same way they already do with tanks and machines elsewhere in the mod:
- **Item slot:** standard right-click interaction, same as tanks/machines.
- **Fluid tank:** a **second, GUI-only item slot**, dedicated purely to holding a player's fluid-handler item (bucket/Beaker) for manual fill/drain — filled container drains into the tank, empty container fills from it, direction auto-chosen (reusing the existing `ModFluidUtil` transfer pattern already used by machine tanks). This slot is **never exposed to the automation-facing `IItemHandler`** for any direction — a hopper or duct cannot see or touch it, so there's no race between a player draining fluid and the network pulling from the same slot.
- **Same physical tank, deliberately.** The manual slot drains/fills the *same* 1000 mB buffer tank the network uses — not a separate mini-tank. The entire point of manual access is to let a player clear a stuck buffer or run fluid through a junction to test a section, so a logically separate tank would defeat the purpose. This means a player can, in principle, drain fluid that's actively mid-transfer through the network on the same tick — considered acceptable and intentional, not a bug to guard against.

## Milestone status (as of this session)

**Tier-1 Innards Duct block: rendering milestone complete.** Places, connects (arm→duct, end-flange→machine, nothing→air), renders via multipart with the smooth node-hub. Corners = two arms (no elbow). Classes: `block/custom/duct/` — `DuctConnection` enum, `AbstractInnardsDuctBlock` (inheritance-ready base, six per-face enum props, no BE), `InnardsDuctBlock` (Tier 1). Item uses the flat `innards_duct_icon`. Collision is a core-sized 12px cube (`2–14`); the thin arm/end stubs are non-solid on purpose.

**Duct connection logic — final model: persistent slot-commit (`AbstractInnardsDuctBlock`), superseding the earlier positional/mutual model (bug found and fixed 2026-07-10).** A duct is a **non-branching, two-ended** conduit (`maxConnections()` = 2); branching is exclusively the **Node's** job. Each duct's 6 `DuctConnection` face properties are the **persistent source of truth**, not a value recomputed from scratch on every neighbour change:
- `getStateForPlacement` — a newly placed duct commits to at most `maxConnections()` neighbours (fixed direction order, first-fit), but only attaches to a **duct** neighbour that still has a free slot (`countConnections(state) < max`); Node/machine neighbours always accept. An already-complete run's segments read as full, so a corner placed alongside an existing leg can't attach to — or steal a slot from — that leg.
- `updateShape` — touches **only the one face** toward the changed neighbour, preserving the other faces' existing commitments untouched. Duct-duct connections are symmetric: a face only becomes `PIPE` if the neighbour already points back (`reconcileFace`); a face is cleared only when the neighbour is positively gone or stops connecting back.

**Why this shape (history — three earlier attempts were buggy).** (1) First impl wrongly allowed all 6 faces (no cap). (2) A `countConnections`/`hasRoomToConnect` "room check" was added, but made connections depend on *other ducts' connection-property values* filled in an order-dependent cascade — orphaned hubs, one-sided arms. (3) The fix for that was a **pure positional function + mutual pairing**: connection state computed purely from neighbour block *types* (never other ducts' state), first-N-by-`Direction.values()`-order with mutual pick-back required for duct-duct pairs. This looked clean and order-independent and shipped for a while, but broke on a real, common case: **placing a corner duct next to an already-complete straight leg.** The corner is face-adjacent to 3 ducts (2 intended corner neighbours + 1 incidental brush against the parallel leg) — geometrically indistinguishable from an intentional branch to a stateless function, so global-priority picking could grab the wrong two and silently orphan the real connection ("sections with one connection will not connect," specifically near corners). The fix was to stop being purely stateless and instead let each duct's connections be **persistent and slot-limited**, as above — a full leg is recognizably full to a new neighbour, so it's never mistakenly attached to or starved. `DuctRunResolver`/`NodeBlockEntity.isConnected` (which read the properties directly) are unaffected — they still see a stable, non-oscillating state, just backed by commitment instead of by recompute. Note: a `null`/`LevelAccessor` (vs full `Level`) can't run capability queries; on those updates a non-duct/non-node face's existing commitment is left untouched rather than risk clearing a live machine connection. See [[feedback_duct_connection_slot_commit_model]] in Claude Code memory for the full incident writeup. **Known accepted limitation:** removing a duct does not auto-reconnect a previously-refused neighbour into the freed slot — players re-fiddle pieces to reconnect (intentional simplicity, not a bug).

**Machine ↔ Node direct adjacency (as-built, implemented 2026-07-10) — partially supersedes the "machine drain via ducts" plan below.** Two related fixes, both prompted by the same observation: a machine set directly against a Node (no duct segment in between) needs to work correctly in both directions.
- **Auto-push must not bypass a Node.** Every machine's existing "push fluid to the block directly above/below every tick" behaviour (`ModFluidUtil.pushFluidToNeighbour`, used by `pushFluidToAboveNeighbour`/`pushFluidToBelowNeighbour`) now bails out immediately if that neighbour is a Node (`instanceof AbstractNodeBlock`). Without this, a machine touching a Node would dump fluid straight into its tank — unlimited amount (`Integer.MAX_VALUE` transfer), every tick, completely ignoring the target leg's direction mode and Fluid toggle — bypassing the entire "every hop is a Node decision" design law. A Node is never a passive auto-push target; it must always be pulled from deliberately via its own `IN` leg + Fluid toggle, exactly like any duct-mediated source.
- **A Node now recognises a directly-touching machine (or another Node) as a valid leg, with no duct segment required.** `DuctRunResolver.resolve` already treated an immediately-adjacent non-duct block as a valid zero-hop `Endpoint` (this was already true before today, just never reachable in practice) — the missing piece was `NodeBlockEntity.isConnected(dir)`, which previously required the neighbour to be a duct with a `PIPE` connection. It now also accepts a neighbour that exposes an item or fluid capability directly on the touching face (a plain machine, or another Node — Node's own capabilities count too, so direct Node-to-Node adjacency works the same way duct-mediated Node chaining does). No blockstate/rendering change needed on either block — the Node has no per-face visual state to update, and the GUI already asks `isConnected(dir)` to decide which leg buttons to show, so a butted-up machine's leg just appears.

**Machine-direct duct drain (as-built, implemented 2026-07-10) — this is the actual shape the "wider footprint" plan above turned into, and it's deliberately Node-less.** A machine can now reach a target machine within the 3x3 footprint directly below it by routing straight through a duct run, with no Node anywhere on the path. This was a real design fork (confirmed with the user before building): earlier plans assumed every hop had to go through a Node; this feature is a **deliberate exception** to that law specifically because the common case ("stack two machines a block apart, connect with ducts") doesn't need real routing, just a straight local drop -- Nodes remain mandatory for anything that needs actual distribution/direction decisions.

- **Reach bound (confirmed):** the resolved endpoint (and every duct hop along the way) must stay within `|dx|,|dz| <= 1` of the source machine and strictly below it (`y < sourceY`), via `DuctRunResolver.resolveWithinFootprint`. Also capped at `DuctRunResolver.DRAIN_MAX_HOPS = 8` hops. Both bounds exist for the same reason: keep this a local drop, never a base-spanning backbone -- that's what Nodes are for.
- **A Node anywhere on the path still blocks the drain.** If the duct run ends at (or the source is directly touching) a Node, nothing is pushed -- unchanged from the existing "Nodes are pulled from, never pushed into" rule. A player who wants a Node-routed drain sets that Node's leg to `IN` + the relevant toggle instead.
- **Fluid AND items, confirmed in scope (a deliberate widening from the original fluid-only plan).** This required a genuinely new behavior: machines previously never proactively pushed items anywhere (they only exposed a DOWN output slot for something else to *pull*, e.g. Metastasizer's `OUTPUT_SLOT`). The drain feature makes that symmetric with how fluid machines already auto-push -- `MetastasizerBlockEntity` now actively drains `OUTPUT_SLOT` downward every 5 seconds (mirroring the fluid machines' existing `RESULT_TANK` drain cadence), via the new `ModItemUtil.pushItemToBelowNeighbour`/`pushItemToNeighbour` (a direct mirror of `ModFluidUtil`'s equivalents, same Node-bypass guard, same duct-walk path). Items are **not** tier-gated (see below) -- only fluid hazard tier is a concept.
- **Duct fluid-hazard tier (confirmed, new concept -- this is the part that gives duct upgrade tiers a real reason to exist beyond throughput).** Because this path can move fluid across a duct run that never touches a Node's tank, there was no longer anywhere for the existing tank-based hazard gate (`VulnerableTank`) to catch a hazardous fluid. Fix: `AbstractInnardsDuctBlock` has an abstract `hazardProfile()` (Tier 1 `InnardsDuctBlock` returns `HazardProfile.TIER_1`, the same profile `VulnerableTank` uses); `DuctRunResolver` **intersects** every duct's profile crossed during a walk (seeded from `HazardProfile.ALL` — a zero-hop run tolerates everything) and returns the combined profile on the `Endpoint`. This is enforced identically on **both** paths -- the direct drain, and the pre-existing Node pull/push (which previously only checked the Node's own tank tier, not the duct path's) -- so a Tier 1 duct segment can never secretly carry a fluid its own profile rejects, regardless of what's pulling/pushing through it. A future duct upgrade tier just overrides `hazardProfile()` to return a higher preset (or a preset `.plus()` an off-ladder hazard); no other code changes. **`HazardProfile` (as-built, code-level; see also `dermicraft-project-primer.md` → Hazard tag hierarchy) models tolerance as a *set* of tolerated hazard tags, not a linear tier int** — `intersect()` is the set-model form of weakest-link, and `accepts(fluid)` passes iff every hazard tag the fluid carries is in the tolerated set. This is what let the Metaphysical (Mild/Severe) hazard tags be added later without touching the Tier 1–4 ladder presets at all.
- **Receiving-side face routing works for free, no adjustment needed (confirmed important detail, checked before building).** Both the direct-adjacency push and the duct-walk push resolve the target through `getCapability(..., endpoint.accessDirection())` -- the exact face the connection touches. This means the *receiving* machine's own per-face input/output rules (e.g. a machine's `RESULT_TANK` on its own DOWN face rejecting external fills) are respected automatically, the same as the Node's pull/push already did. A player has to aim the drain at an actual input face; wiring into an output-only face just silently transfers nothing.
- **Implementation:** `ModFluidUtil.pushFluidToNeighbour` (the single choke point every fluid machine already calls) now branches: DOWN into a duct walks the bounded run via the new path instead of the old direct-capability lookup; everything else (including the existing Node-bypass guard) is unchanged. Because this is one shared choke point, the four existing fluid machines (Effluencer, Masticator, Drooling Cauldron, Skin Tank) got duct-drain support with **zero changes to their own code**.

**Node block: rendering pass in-game (as-built).** `block/custom/duct/` — `AbstractNodeBlock` (inheritance-ready base) + `NodeBlock` (Tier 1). Registered as `innards_node` ("Innards Node"), non-directional full cube (no `FACING`, like Skin Tank): **top face = `textures/block/innards_duct/node_face.png`** (red intake port + north-pointing arrow, so the fixed orientation reads as north), other 5 faces = `skin_tank_end`. Ducts recognise a node as a valid pipe endpoint (`canConnectToPipe` now matches `AbstractNodeBlock`), so a duct renders an arm into a node and it counts toward the duct's 2-end cap. **No BE/buffer/routing/GUI yet** — rendering only.

**Break / pickup behavior (confirmed, as-built) — duct & node are the drop-self exception.** Mod-wide rule: every block is destroyed on a normal break and recovered only by the right pickup tool (Forceps + `COLLECTIBLE` tag). **Ducts and Nodes deliberately break that rule: they drop themselves on a normal break** (real drop-self loot tables, not `noLootTable`) so players aren't punished for the constant re-fiddling pipes require — while *still* keeping the Forceps pickup (they're in `COLLECTIBLE`). See [[project_block_pickup_and_break_rules]]. **Future Node BE break rule:** when the node's buffer exists, a break **drops the buffered items but does NOT spill the fluid** (fluid voided silently, no mess) — same no-punishment reasoning; unlike the tank family which spills/preserves.

**Node BE + first-pass GUI (as-built, NO routing logic yet).** `NodeBlockEntity` (`block/entity/custom/`) extends `MachineBaseBlockEntity` + `MenuProvider`: a 2-slot `INVENTORY` (slot 0 = transport item buffer; slot 1 = **GUI-only** fluid-handler slot that fills/drains the tank on change — the manual jam-clear/test interaction) + a 1000mB tank. Break drops the buffered items, **not** the fluid (`drops()` → `super.drops(INVENTORY)`; block `onRemove` calls it). `AbstractNodeBlock` now extends `ModBaseEntityBlock` (empty-hand right-click opens the menu via `useWithoutItem`); `NodeBlock` supplies codec + `newBlockEntity`. Registered: `INNARDS_NODE_BE`, `INNARDS_NODE_MENU`, `NodeScreen`, and the `FluidHandler.BLOCK` capability (tank only — item automation deliberately *not* exposed yet, so the GUI-only fluid slot stays unreachable by pipes). GUI (`NodeMenu`/`NodeScreen`, `screen/custom/node/`): background + tank gauge (`tank_and_slot` + 16x40 `FluidTankRenderer`) with the fluid-handler slot at its base + a buffer `item_slot`. **Slot/widget positions are placeholder first-pass** — to be refined with the composited-layout approach.

**Mod-wide Tier hazard restriction (confirmed, as-built).** The Node's tank is a **`VulnerableTank`** (constructed with `HazardProfile.TIER_1` — the same Tier 1 restriction every other Tier 1 tank in the mod uses, e.g. Masticator's ingredient/result tanks), not a plain tank. **Ducts need no separate check at all** — a duct has no block entity/fluid state of its own; the Node's tank is the *only* place fluid ever sits anywhere in the whole system, since every hop (pull from a source, push to a destination) passes through it. Gating that one tank's validator is therefore sufficient to protect the entire duct network for free. This also exposed and fixed a real bug in the pull-phase transfer: draining from the source *before* confirming the tank will accept the fluid would have silently voided a rejected hazardous fluid (drained out, then thrown away on a failed fill) — `pullFluidFrom` now does a `TANK.fill(..., SIMULATE)` check before ever draining the source for real. Future upgrade tiers that should tolerate higher-hazard fluids (per the mod's cumulative Tier rule) just need a different tank subclass/validator here — no duct-side changes required, ever.

**Routing GUI (as-built, confirmed working in-game).** Every one of the 6 compass positions always shows a button: `null_button` where there's no connection, otherwise the compass texture (its `_pressed` variant when that leg is the one currently selected). **Interaction model:** click a connected direction to select it (highlight = pressed texture); the single shared In/Out button then cycles *that selected leg's* mode (In → Out → Off) and its own texture reflects the selection's current mode (`null_button` when nothing selected). Round-Robin/Spread is a separate always-active global toggle, no selection needed. `NodeDirectionMode` (IN/OUT/OFF) and `NodeDistributionMode` (ROUND_ROBIN/EQUAL_SPREAD) enums live in `block/custom/duct/`, state stored on `NodeBlockEntity` (`Map<Direction, NodeDirectionMode>` + one `NodeDistributionMode` field), NBT-persisted. Client→server clicks go through a new networking layer (`network/` package — `NodeDirectionClickPayload`, `NodeDistributionClickPayload`, registered in `ModNetworking` the same `@EventBusSubscriber` way as `ModBusEvents`); server mutates the BE and calls `setChanged()/updateBlock()`, which syncs back to the client for free via the same full-NBT update-packet mechanism Masticator's health/progress already use — no bespoke sync code needed. **Known simplification, accepted for now:** `null_button` is reused both for "no connection" and for "nothing selected" on the shared In/Out and Item/Fluid toggle buttons — a distinct texture can be added later if the overlap becomes confusing in practice. (The earlier-planned "mode-locked" state this was originally reserved for was dropped along with the mode-lock design itself — see Item/Fluid toggles, above.)

**Flow/transfer logic (as-built).** `DuctRunResolver` (`block/custom/duct/`) walks a duct run out from a Node leg — a duct is strictly two-ended, so it's always a straight walk: at each hop, confirm the duct's incoming face is actually committed (`PIPE`, per the persistent slot-commit model above), then step through its one other connected face, until hitting something that isn't a duct. `NodeBlockEntity.tick()` runs on the standard `CRAFT_TICKS` (10-tick) cadence: **pull phase** (every `IN` + connected leg with at least one type enabled tries to drain fluid — if that leg's Fluid toggle is on — and/or extract an item stack — if its Item toggle is on — from its resolved endpoint) then **push phase**, computed **separately per type** (a leg can be an eligible OUT leg for items, fluid, both, or neither, independently): per `distributionMode`, **Equal Spread** splits each type's current buffer amount evenly across that type's own eligible `OUT` legs (partial delivery accepted, leftover retried next cycle); **Round-Robin** sends the full available (rate-capped) amount of each type to one leg per cycle, each type advancing its **own** persisted cursor (`itemRoundRobinIndex` / `fluidRoundRobinIndex` — separate from each other, since the eligible leg set can differ per type). **Flow amount restrictions (explicit ask, implemented):** `ITEM_TRANSFER_PER_CYCLE = 4` and `FLUID_TRANSFER_PER_CYCLE = 100` (mB) cap how much moves per leg per cycle — placeholder values, tune freely, but transfer is never unlimited-per-tick, so running both types on a leg simultaneously (see Item/Fluid toggles) is not a server-load concern.

**Node-to-Node chaining (confirmed, implemented 2026-07-10) — supersedes the earlier "Node-to-Node returns empty" limitation.** A duct run ending at another Node is now a valid endpoint, resolved and gated exactly like the pre-existing "two Nodes disagreeing on a shared leg = inert" rule from the Node section above, now actually enforced in code rather than just documented:
- `DuctRunResolver.resolve` no longer special-cases hitting a Node as empty — it returns it as a normal `Endpoint` (pos + the face touching the duct, which equals that Node's leg direction since Nodes have no rotation). The only rejected case is a run that loops straight back to its **own origin Node** (self-loop guard, `nextPos.equals(nodePos)`), so a Node can never try to push/pull into itself.
- `NodeBlockEntity.targetNodeAccepts(level, endpoint, requiredMode)` gates every pull/push against that rule: a **push only lands if the target Node's matching leg is `IN`**; a **pull only succeeds if the target Node's matching leg is `OUT`**. A plain machine endpoint has no leg concept, so it's always allowed (unchanged behaviour). This means a two-Node run with legs set correctly (one `OUT`, one `IN`) now actually relays; one set wrong (both `OUT`, both `IN`, or the target leg `OFF`) is inert, exactly per the documented rule.
- **Chaining through several Nodes to a distant machine falls out for free** — no separate "machine-and-node chaining" feature was needed. Each Node just forwards whatever lands in its buffer on its own next `CRAFT_TICKS` cycle via its own `OUT` legs; a chain A→B→C is just A's push landing in B's buffer, then B's own tick pushing that into C (a machine or another Node) on the next cycle. Multi-hop transfer is therefore inherently staggered by one 10-tick cycle per Node hop, not instantaneous end-to-end — an accepted consequence of the buffer-relay design, not a bug.
- **Item automation capability is now registered externally** (`ModBusEvents`, `Capabilities.ItemHandler.BLOCK` → `NodeBlockEntity::getItemHandler`), reversing the earlier "deliberately not registered" call — chaining requires the Node's buffer to be reachable via the standard capability lookup the same way a machine's is. To keep the GUI-only fluid-handler slot (`FLUID_ITEM_SLOT`) safe from hoppers/ducts/other Nodes despite this, `getItemHandler(Direction)` now branches: `null` (menu/GUI) still returns the full 2-slot `INVENTORY`; any real direction (a capability query) returns a `RangedWrapper` restricted to `BUFFER_SLOT` only — same face-restricted-wrapper convention already used elsewhere in the mod (e.g. Effluentcer's per-face tank routing).
